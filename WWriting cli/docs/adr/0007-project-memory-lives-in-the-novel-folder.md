# WWRITING.md 属于作品，进创作目录

`WWRITING.md` 放在**创作目录**（`<projectRoot>/WWRITING.md`），与其它作品文件并列。
它是用户可查看、可手工编辑的项目记忆入口——所以它必须在用户找得到的地方。

**为什么这和 ADR-0002 不矛盾**

ADR-0002 说「应用私有历史不进创作文件夹」。`WWRITING.md` **不是应用私有数据**：
会话、事件日志、成本、API Key 属于应用运行状态；`WWRITING.md` 属于**这部作品**。
判据是「这文件是作品的一部分，还是应用的运行痕迹」。

**Consequences**

- **只能由模型经既有 `write_file` / `edit_file` 写入**，因此天然走权限确认
  （`src/tools/permissions.mjs` 的 `WRITE_TOOLS`）。应用代码**不得**自动生成或修改它。
- `scripts/smoke-windows.ps1` 那条「创作目录里没有私自生成的 `WWRITING.md`」断言，
  守的就是这条——它要断言的是「**应用**没私自生成」，不是「**模型**没经确认生成」。
  改动该断言时不要把它放松成后者。
- 它与 `OUTLINE.md` / `SETTING.md` / `AGENTS.md` 是同层的东西：都在创作目录，
  都是用户的资产。`WWRITING.md` 的特殊之处只是**它是索引兼记忆**，不是第二份总纲。
- 多进程同时写它时：**最后写者赢**，不引入新的锁（Q12，2026-09-28 访谈拍板）。
  它和用户在编辑器里同时打开它没有区别——给创作目录加锁会违反 ADR-0002。
  防线不是锁，是**可见性**：模型改它时确认卡必须显示改了什么（旧→新的 diff 摘要）。
- **补记（2026-09-29）**：上面这条「确认卡必须显示改了什么」在本次实施中**推迟**了
  （决策 P8）。当前落地的只有第一道防线——system prompt 里的谨慎合并职责
  （统一行为规格书:375 原文）。因此本 ADR 承诺的「可见性防线」目前只有一半：
  模型整体覆盖用户手写内容时，确认卡仍然只显示「写入文件 WWRITING.md」，
  用户看不到改了什么。
  推迟的理由不是「不重要」，而是它需要把旧内容读出来、算 diff、再经
  `permissions.request` → `decision_pending` 事件 → `printDecision` 一路带到屏幕上，
  而这条链路上还得先定「diff 多长时怎么折叠」——那是一次独立的交互设计，
  不该混在项目记忆的首次落地里。
  **补上它之前，不要放松 `scripts/smoke-windows.ps1:281` 那条断言**：
  它是目前唯一还在守着「应用没私自生成 WWRITING.md」的检查。
