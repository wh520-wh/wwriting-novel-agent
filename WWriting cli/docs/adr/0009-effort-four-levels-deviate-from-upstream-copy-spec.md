# /effort 直通 API 四档，刻意偏离上游的「低/中/高」文案规格

`/effort` 暴露 DeepSeek API 的四档 `none` / `low` / `high` / `max`，不做上游那套
「低/中/高」三档抽象，也不加中文别名。

**Context**：AGENTS.md 把上游 `D:\WWriting` 定为「能力与文案的**规格权威**」，
而统一行为规格书:156 的原文是「思考强度仅当模型已验证支持时显示 低/中/高，
否则只显示 `自动` 且禁用，不伪装生效」。四档直通**偏离**了这句话的前半段
（后半段的「仅当已验证支持」「不伪装生效」被完整继承，见 D9 的三层能力判定）。
偏离不一定是错的，但它的性质是**规格决策**，不能当成顺手的产品选择——所以落这条 ADR。

**Considered Options**

- **三档 低/中/高（不偏离规格）**：与桌面版观感一致。但 `中` 只能映射到 `high`，
  于是 `max` 这一档整个丢掉——而 `max` 是真实能力差异，不是装饰：
  官方文档写明 `max_tokens` 的服务端默认值随档位变化（非思考 8K / 思考 64K / **`max` 时 128K**）。
  对长篇写作来说，输出上限从 64K 到 128K 是「一章能不能一次写完」的差别。
- **四档 + 中文别名（`/effort 关|低|高|最强`）**：看着亲切，但会给「哪个词对应哪个档」
  留出歧义空间（「低」是 `low` 还是「比 high 低一档的 medium」？）。这里要的是精确。
- **四档直通（选中）**：与官方文档一致，用户查文档时能对上；`max` 不白丢。

**Consequences**

- 文案与桌面版不一致：同一个产品的两个前端对思考强度的说法不同。
  这是**已知代价**，不是疏忽——CLI 直连 DeepSeek，没有上游多厂商 UI 的抽象层，
  那层抽象在这里只是损耗。
- 官方文档的兼容别名（`minimal` → `low`，`medium` / `xhigh` → `high`）在解析层被接受，
  但**不主动展示**：`/help` 与 `/effort` 回显里只出现四档本名。
  收它们是为了让用户从别的工具带过来的肌肉记忆不至于撞墙。
- 编码按 DeepSeek 官方「思考模式」文档的 OpenAI 格式适配：`low/high/max` 双发
  `reasoning_effort` + `thinking:{type:"enabled"}`；`none` **只发** `thinking:{type:"disabled"}`、
  不发 `reasoning_effort`（官方 OpenAI 格式的枚举只有 low/high/max）。绝不赌服务端默认——
  2026-08 实测默认值按时间窗漂移，思考内容时有时无。
- `none` 档会对支持它的模型下发 `thinking:{type:"disabled"}`。
  这对 GLM-5.3 系列是**直接报错**的（`docs/research/04-llm-api-agent-core.md:130`），
  所以能力判定的第 (ii) 层允许网关用户声明一个不含 `none` 的档位集合。
- **未决项：能力表不做真实端点实测**（2026-09-29 用户决定）。档位集合与 `max_tokens` 的联动
  是服务端行为、本地无法终验；本次改为按官方文档适配 + 本地测试钉住编码规则，
  依据是 `docs/research/06-deepseek-reasoning-effort-probe.md`。真实联调的行为观测留给上线后；
  若与官方文档不符，改 `OFFICIAL_REASONING_CAPABILITIES` / `OFFICIAL_MODEL_LIMITS` 两处即可。
- **与铁律 10（全部 UI 文案使用简体中文）有一处张力**：档位名 `none/low/high/max` 是英文。
  P11 豁免的是**档位名**（它们是 API 的字面取值，用户查文档要能对上），不是整句话。
  所以「回到自动」显示为中文 `自动`，输入 `自动` 与 `auto` 都收；
  `/help` 里那一行写作 `/effort none|low|high|max|自动`——英文档位 + 中文的「自动」。
  这处混排是刻意的，记在这里免得下一个人来「统一」它。
- **能力判定的三层顺序与草案 D9 的编号相反**（审查要求显式声明的偏离）：
  D9 写的是 (i) 官方内置表 → (ii) 配置声明 → (iii) 判不支持，「逐层回退」；
  实现是 **(ii) 配置声明优先于 (i) 内置表**。理由是「用户明说的」应当压过「代码里写死的」——
  官方端点下也会出现内置表还没收录的新模型，此时声明是唯一出路；
  反过来（表优先）会让用户明明声明了却被静默忽略。
  两者的差异只出现在一种情形：官方端点 + 模型在内置表里 + 用户又声明了一个不同的集合。
  此时按声明走。
- **「自动」不等于「什么都不发」**：模型已验证支持思考时，自动 = 按 `DEFAULT_EFFORT`（`high`）双发；
  判不出能力时才一个字段都不发。若把自动实现成「不下发任何字段」，就是在赌服务端默认——
  而 §六 与本 ADR 的 Context 明令禁止。上游 `openai-compatible.mjs:122-131` 同样把 auto 映射到默认档位。

**未决项**

- **档位不持久化**。上游把三控件定为「选择即保存为项目默认」，本实现只在会话内有效，
  重启回到 `自动`。理由是思考强度依赖模型能力，而模型可以随时切；
  持久化一个「项目默认档位」就会在切模型后留下一个可能无效的档位。
  真要持久化，前置条件是先把「档位跟模型走」这件事设计清楚
  （每个模型记一个默认档位，而不是整个项目记一个）。
- **`syncWithModel` 只在 `/model` 保存时被调**。用户直接编辑 `config.json`
  或用 `DEEPSEEK_MODEL` 换模型时，档位要等到下一次 `/model` 保存才会被校验并「如实说一句」。
  这**不会**造成错误请求——`requestLevel()` 在每次组请求时都会再判一次能力，不合法就不发；
  缺的只是那一句提示。
- **能力表需要按官方文档维护**。`OFFICIAL_REASONING_CAPABILITIES` 与 `OFFICIAL_MODEL_LIMITS`
  的取值出处是 `docs/research/06-deepseek-reasoning-effort-probe.md`（2026-09-29 起为
  「按官方文档适配」，**不再做端点实测**）。官方端点上出现新模型时，
  这张表不会自动跟上——此时用户走第 (ii) 层自己声明，或者等表更新。
- **`max_tokens` 无条件下发，对非官方端点是一处刻意接受的代价**（2026-09-29 终审收口）。
  P28 要求「给足空间、不赌服务端默认」，所以每个请求都带 `max_tokens`：
  官方模型按其输出上限，非官方端点 / 未知模型按回落值 **65,536**。改动前这个字段**不发**，
  由服务端默认兜底——因此 `base_url` 指向的网关模型若真实输出上限低于 64K（4K/8K 那类），
  现在会被 400 打回。这与 P12「绝不乐观下发服务端可能拒绝的值」是同一类风险，
  只是这里**没有本地闸门**（`GET /models` 不返回能力信息，判不出来）。
  取舍：用户明令「给足空间」，且无法自动判定网关上限，所以**保留下发**，
  代价写进 README 的网关段与 `docs/research/06` 的「可能与官方不一致」一节，
  让网关用户知道要自行声明或绕开。将来的出路是给 `config.json` 加一个
  `max_output_tokens` 声明字段（与第 (ii) 层的 `reasoning_effort_levels` 同一形状）。
