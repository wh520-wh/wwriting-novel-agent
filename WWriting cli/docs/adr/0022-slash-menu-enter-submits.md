# 斜杠菜单回车语义：提交原文（有意偏离上游 §4.7 的「Enter 只填入不执行」）

上游统一行为规格书 §4.7 的补全菜单契约：「支持前缀筛选、上下键、Enter、Tab、Esc 和鼠标
选择。选择命令只把完整命令填入输入框，不自动执行」——Enter 与 Tab 同为「填入」，要执行
还得再按一次。本决定落地的斜杠联想菜单（工单 04/05/06）**采纳其中前缀筛选、上下键、Tab、
Esc 四项**，对 Enter 一项做了有意偏差，鼠标项终端无对应物（平台差异）。

## 决定

1. **Tab = 填入（与上游一致）**：把高亮命令补全进输入框（带尾空格），不执行——留给用户
   补参数（如 `/resume <ID>`）。
2. **回车 = 提交原文（偏差）**：菜单开着时回车不补全、也不执行高亮项，提交的是输入框里
   的原文——完整命令照常执行，不完整前缀走既有的「不认识 这个命令」反馈。这与
   Claude Code 2.1.88 的按键表一致（Autocomplete 上下文只绑 tab/escape/up/down，
   Enter 落到 Chat 层原样提交）。
3. **理由**：菜单高亮着 `/model` 时按回车，用户的预期是「就是它」——「先填入再回车」
   的双重确认在终端里是多余的一步；而「回车=执行高亮项」又会替用户猜（打到一半的
   `/mo` 回车变成执行 `/model`）。提交原文 + 底部常驻按键提示行
   （`↑/↓ 选择 · Tab 补全 · Esc 收起`）两头都不猜。
4. **配套纪律**：菜单底部提示行必须常驻——本菜单的「回车」与全 app 五处选择器的
   「回车确认」相反，不给提示就是埋雷（铁律 3 的「文案极简」以这一行为代价，评审裁定值得）。
5. **空 `/` + 回车 = 无操作**：旧「空 / 回车开弹窗」交互随本功能退役；裸斜杠与空行共用
   输入层同一个丢弃闸。

## Considered Options

- **跟上游 Enter=填入**：与规格书逐字一致，但多一步；且菜单「回车确认」与五处选择器
  的「回车确认」撞车，肌肉记忆反而混乱。
- **回车=执行高亮项**：最快，但打到一半的前缀回车会替用户做决定——违反「菜单只联想、
  不替用户猜」的边界（用户故事 8）。

**有意不做**：不做参数补全（`/resume <会话ID>`）；不做文件路径 / @ 联想；不做鼠标选择。
