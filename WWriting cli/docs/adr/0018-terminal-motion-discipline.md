# 终端动效纪律：唯一受控 spinner，运行态才推进，终态 0 循环动效

上游 §7 的动效条款（shimmer、流式光标、`prefers-reduced-motion`）是 Web 语言；终端侧
真正的取舍是：**要不要让全库出现第一个定时器**。长期现状是「零定时器、零循环动效」
（`renderer.mjs` 明写着「没有定时器，也就没有空转的事件循环」）——代价是长工具执行、
无思考流模型的静默期里屏幕一片死寂，用户分不清「在干活」还是「卡死了」。参考实现
grokbuild 与 Claude Code 的终端都用「运行态才推进」的 spinner 解决同一件事。

落地为一条纪律 + 一个实现：

1. **唯一性**：全库只有一个循环动效——实时区动态行的 braille 帧字符
   （`SPINNER_FRAMES`，120ms/帧，`style.mjs`）。帧字符顶替动态行的标记位：活动行的
   `•` 原位换帧，状态行/思考预览前置成「状态点 + 文案」（对齐上游 summary 形态）。
   文案不动——2–6 字纪律不因动效破例；耗时仍在终态才出现（`思考 N 秒`）。
2. **生命周期**：运行态动态行出现时懒启动；**终态状态行、让位写 scrollback、关闭**
   三处必停，tick 自身发现动态行没了也自收摊——任何时刻至多一个定时器，
   终态 0 循环动效。正文路径（printAssistant）不碰时钟，「一行一行冒出来」的流式感
   不变。管道（无 composer）没有实时区可重绘，永不启动。
3. **注入**：时钟经 `scheduleTick` 注入（默认 `setInterval`），与 `columns` 函数注入
   同一条纪律；测试用手动步进的替身。**测试替身一律不装真实时钟**——直连
   createRenderer 的用例漏传时钟，一条运行态动态行就是一条真实 120ms 定时器，
   测试进程会被事件循环吊住不退出（真实踩到）。

**Considered Options**

- **保持零动效并写成纪律**：架构最干净，但死寂问题无解，且与两个参考实现的终端
  惯例相悖——「活着」本身是过程可见性（铁律 2 的精神）的一部分。
- **spinner + 运行中实时秒数**：信息更足，但上游文案表的运行态没有耗时位
  （耗时只在终态出现），突破 2–6 字文案纪律，否决。
- **事件驱动的伪动效（仅在事件到来时换帧）**：事件稀疏的静默期恰是不动的时候，
  等于没解决，否决。
- **唯一受控 spinner + 注入时钟（选中）**：死寂问题解决，纪律用「至多一个定时器 +
  三处必停 + 测试断言收摊」钉住。

**有意不做**：不引入 shimmer/渐变等富动效（终端无 -> 需要 SGR 空间动画，超出克制
原则）；不给 spinner 做「降低动效」环境开关——帧推进是唯一动效且只动一个字符位，
比 NO_COLOR 的色彩负担还低；排队行、计划面板、正文不参与动效。

顺带修复的两个既有缺陷（同属「动效与实时区」的卫生）：

- `select.mjs`：光标隐藏（`?25l`）之后按键处理若抛异常，`finish` 不跑，光标永久
  隐藏——`onKey` 补 catch 兜底恢复，不吞异常。
- `renderer.mjs endLive`：挂起期间（composer 未激活）refreshLive 早退，「清空实时区」
  送达不了输入层而去重记录未作废——恢复后同一份动态行会被去重吞掉。endLive 在
  早退路径上作废 `lastLiveSet`。
