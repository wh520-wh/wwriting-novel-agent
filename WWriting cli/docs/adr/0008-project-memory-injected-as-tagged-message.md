# 项目记忆作为带标记的独立消息注入，不塞进 system prompt

`WWRITING.md` 的内容作为一条**独立的合成 user 消息**注入，位置在 system 之后、
历史之前。它带一个可识别的标记（如 `[Project Memory: WWRITING.md]`），
**不要**把内容拼进 system prompt 字符串。

**Considered Options**

- **塞进 system prompt**（上游桌面版的做法）：改动最小，且上游把它当「受信任的
  项目指令层」（与 `AGENTS.md` 同层语义，不套 untrusted 数据包装）。但本项目的
  system prompt 是一个 4 行模块级常量，历史回放的 `estimateChars` 预算、回放投影、
  屏面统计**都看不见 system 里的东西**——内容一旦塞进去就脱离了这些机制。
- **独立合成消息**（选中，借鉴 grokbuild 的 `ProjectInstructions` 标记）：
  结构上可与真实用户输入区分，能被算进预算、能被回放排除、屏幕可选择是否呈现。
  代价：多一种「合成的 user 消息」要处理，任何遍历 messages 的代码都要知道它不是用户说的。

**Consequences**

- 遍历 messages 的代码（历史投影、预算估算、渲染归属）必须能区分它。
  给出它一个明确的来源标记，不要靠「内容长得像不像」来猜。
- 它属于**项目指令层**，优先级低于用户当轮的明确指令、高于历史里的旧对话。
- 若将来用 XML 标签包裹它，**必须先转义内容里的 `<`**——否则用户在 `SETTING.md`
  或 `WWRITING.md` 里写一个闭合标签就能伪造框架结构（grokbuild 做了这件事，
  见其 `neutralize_reminder_tags`）。
- **补记（2026-09-29）**：本次实施用的是方括号标记 `[Project Memory: WWRITING.md]`，
  不是 XML 标签，所以上面那条「必须转义 `<`」暂时用不上。但它换来一个**不同的**残余风险：
  用户若在 `WWRITING.md` 正文里写了一行一模一样的标记，注入消息里就会出现第二个「记忆边界」，
  模型可能把它后面的内容当成另一份项目指令。
  **本次不做防御**，理由有三条：① 那个文件是用户自己的、在自己的创作目录里，
  「伪造」它等于自己攻击自己，没有威胁模型；② 真正需要防的是「被索引的其它文件
  （`SETTING.md` 等）里藏一个标记」，而那些文件是经 `read_file` 进**工具结果**的，
  不走这条注入通道，本来就伪造不出记忆边界；③ 任何中和手段（转义、剥离、加零宽字符）
  都会改动用户原文的字节，而 ADR-0006 的哈希短路依赖「注入内容只由文件内容决定」，
  改字节就要重新论证缓存语义。
  若将来把标记换成 XML 标签，上面那条转义要求立刻生效，且必须连这个方括号标记一起考虑。
- **相邻 `user` 角色是一处已知的兼容性边界**（2026-09-29 终审补记）。记忆消息插在 `system`
  之后、历史之前，于是每个请求喂给模型的数组都是 `['system', 'user', 'user', …]`——system 那条
  合成记忆与用户当轮的输入**角色相邻**，两者都是 `user`（形态钉在
  `tests/agent/run-controller.test.mjs:779`）。DeepSeek 官方端点接受这种排布，但**严格校验
  角色交替的 OpenAI 兼容网关可能拒收**。它与 ADR-0009 未决项里「`max_tokens` 无条件下发」
  影响的是**同一批用户**（自配 `base_url` 的网关）。本次不做「把记忆并进用户消息」之类的改动：
  那会破坏「合成消息可被结构识别、可被回放排除」这条选中方案的根基（见上 Considered Options）。
  若将来要兼容严格网关，正确的方向是在组请求时按端点能力决定是否合并/改写角色，
  而不是改变记忆消息本身的形态。
