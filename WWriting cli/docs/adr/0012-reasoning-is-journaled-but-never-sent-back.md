# 思考正文全量落盘、只经命令查看、绝不回喂模型

模型的 `reasoning_content` 走一条独立通道：客户端经 `onReasoning` 回调收进来，
轮末落**一条** `reasoning_completed` 事件（全文，不截断），屏幕上只画 `思考中` / `思考 N 秒`
两种行（`思考中` 那一行会跟着显示最近两行已完成的思考，见 Consequences 的修订），
全文由 `/reasoning` 按需重放，且**绝不进回喂给模型的 messages**。

**Context**：草案 D14 把这件事拆成采集 / 渲染 / 组装三层，各自独立拍板。
三层的选择分别是 P18（只落一条事件）、P19+P21（全文落盘 + 默认一行 + 命令查看）、
P22（不回传）。它们互相牵制，所以合在一条 ADR 里说清。

**Considered Options**

- **采集**：草案写「新事件 `reasoning_delta` / `reasoning_completed`」。
  上游需要 delta 是为了「运行中最多两行、按自然片段替换」的实时滚尾；
  本项目把这件事交给一条**不落盘的回调**（`onReasoningPreview` → 渲染层的实时区，
  见 Consequences 的修订），日志因此仍然不需要增量事件。
  少一种事件就少掉每轮几百次串行 `append`（写入链是串行的，每条 delta 都排一次队），
  而 `model_delta` 已经在为可见正文付这笔钱了。**只落 `reasoning_completed`。**
- **落盘量**：`max` 档思考可达几万字符，而 `loadHistory` 每轮都 `readAll()` 整个日志。
  截断能省日志，但 `/reasoning` 就不完整了。**选全文落盘**，对齐 grokbuild
  （思考文本原样进 `chat_history.jsonl`）。代价与出路见 Consequences。
- **展示**：终端没有折叠组件。灰显直出全文会把正文冲没（`max` 档几万字符）；
  全局键位（grokbuild 的 ctrl+e）要与常驻 readline 抢键盘。
  **选「实时区两行预览（就地重绘、不进滚动区）+ `/reasoning` 重放全文」。**
- **回传**：DeepSeek 的 thinking_mode 指南（2026-09-28 抓取）说
  「若请求携带 tools，历史轮次的 reasoning_content 均应回传」；
  而本项目 `docs/research/04-llm-api-agent-core.md:159` 引的另一份指南说
  「DeepSeek 明确禁止把 reasoning_content 回传进后续请求」。
  **两份官方材料互相冲突**，而上游对话样式规格书:181 写的是「绝不写入下一轮模型上下文」。
  **选不回传**：两个来源支持它，且上下文与账单可控、历史前缀更稳定。

**Consequences**

- **对上游规格 :176-178 的偏离已收窄到「重绘粒度」**（2026-09-29 修订）。
  原先本实现的 live 行只有 `思考中` 三个字、内容不上屏；现在实时区会跟着显示**最近两行已完成的
  思考**（`思考中 · <第一行>` + 缩进对齐的续行，压暗，`thinkingPreviewLines`）。
  与上游的差别只剩一处：上游按「自然片段」替换，本项目**只在攒满一整行时才重绘**——
  与正文同一条判断（`flushProse` 的注释）：流式逐字到达时每个字都重绘一次，
  会把 readline 按住反复重排，而屏幕上多出来的那点「跟手感」换不回这个代价。
  预览**从不进入 scrollback**：它只活在输入框上方那块实时区里，由输入层原地重画；
  一旦让它像正文那样滚进滚动区，`max` 档几万字符就会把整段正文冲走——那一条没有让步。
  另外，整段思考仍然**不落日志的增量事件**（见上面「采集」那一条）。
- **`/reasoning` 只看本次进程内的上一轮**。思考正文虽然全量落了盘，跨重启的重放
  需要先把整个会话展开，那与「默认折叠」的语义相反。
  因此重启后屏幕上会重演 `思考 N 秒`（ADR-0011），但 `/reasoning` 答不出全文——
  它与「本轮没有思考」**共用同一条 `无思考内容` 主文案**，只在那条 detail 里**始终**带着
  一句「全文不跨重启保留」，把两种可能一并说清。**不能**像上游 `empty` 那样只答
  「本次无输出或该模型不支持」（那会变成一条假事实：屏幕上明明有 12 秒的思考行）。
  用户看到的因此是「两条主文案（`不支持查看` / `无思考内容`）+ 一句始终在场的重启说明」，
  而不是三条各自成句的答复。
- **`events.jsonl` 会明显变大**，而 `loadHistory` 每轮全量读它。
  真成为瓶颈时，正确的做法是给 `readAll` 加一个「只读尾部 N 字节」的入口，
  **而不是**把思考正文截断后落盘——那会破坏日志作为唯一真相源的完整性（ADR-0001）。
- **不回传是对 DeepSeek 现行官方推荐的偏离**。代价：长工具链里模型每轮重新思考，
  思考 token 可能花更多。判据是 D10(b) 收下的 `usage.reasoningTokens`（终态行的
  `（思考 800）`）：跑一轮工具密集任务，若这个数字随轮数线性上涨而不是收敛，
  就该重新考虑回传。**翻这个决定之前必须先解决上面那两份官方材料的冲突**，
  并改上游对话样式规格书:181 的适用范围。
- **`history.mjs` 的投影里永远没有思考正文**，且有一条守门用例钉住它
  （`tests/agent/history.test.mjs:126-137`：断言 `JSON.stringify(projectTurns(...))`
  里不出现 `reasoning` 字样）。需要把思考呈现给人的是 `src/agent/replay.mjs`，
  它自己扫事件——两边各扫一遍是刻意的分工，不是重复。

**顺带记在这里：Q8 的分工**

草案 Q8 定为「与 `AGENTS.md` 分工写清楚即可，不做运行时防御」，但没写落点。落点有三处：

1. **system prompt**（`agent-loop.mjs` 的记忆职责段）：`AGENTS.md` 是**规则**
   （怎么写、什么不许做，相对稳定，由用户维护）；`WWRITING.md` 是**这部作品的当前状态**
   （写到哪了、哪些要求已确认、权威文件在哪，随写作变化，由模型维护）。
   冲突时优先级是「用户当轮的明确指令 > AGENTS.md 的规则 > WWRITING.md 里的旧状态」。
2. **README** 的「项目记忆」小节：同一句话，说给用户听。
3. **本 ADR**：说给将来改这块代码的人听。

不做运行时防御（不去检测「模型把规则抄进了 WWRITING.md」）：那需要一个「什么算规则」的判据，
而判据本身就是一套会漂移的启发式。文字说清 + 用户能直接编辑文件，比一个会误判的检查器强。
