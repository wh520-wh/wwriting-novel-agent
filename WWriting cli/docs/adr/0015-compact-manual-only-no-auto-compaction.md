# /compact 只做手动触发，CLI 不做自动压缩

上游已把自动压缩定为长对话的出路（统一 Journal、上下文窗口与自动压缩规格：安全点触发、
压缩收敛、checkpoint 对账）。CLI 落地 `/compact` 时只做**手动**触发：用户敲命令才压缩，
且只在空闲时可压（忙碌拒绝）；摘要以一条 `digest_compacted` 事件进日志，之后的每轮以
「[会话摘要] + 未覆盖轮次」开工，摘要与轮次合用同一个历史预算（同一本账，不设第二个预算）。

**Considered Options**

- **自动压缩（跟上游）**：触发时机是真正的复杂度——压早了浪费、压晚了丢上下文，安全点要
  与排队 / 停止 / 立即的既有语义对齐，还要回答「压缩失败时这一轮怎么继续」。在字符预算
  （ADR-0005）加 WWRITING.md 手动承载设定的现状下，收益配不上这份复杂度。
- **只做预算截断（什么都不做）**：ADR-0005 解决了「怎么数」，没解决「丢了怎么办」——
  长篇写到几十轮，早期设定全靠用户手动搬进 WWRITING.md，丢前情是真实痛点。
- **手动 `/compact`（选中）**：长篇写作天然有「一章写完了」这样的人工安全点，触发时机
  交给人最合适；实现只压「当时的全部未覆盖轮次」，没有并发、没有安全点问题。
  已知代价：用户不敲命令就永远不压缩，超预算的轮次照旧被截断——这与截断的既有
  语义一致，不算倒退。

后续若做自动压缩，入口就在 `run-controller` 的 `compact()`：把「用户敲命令」换成
「Run 边界的安全点判定」，摘要与注入路径不用动。
