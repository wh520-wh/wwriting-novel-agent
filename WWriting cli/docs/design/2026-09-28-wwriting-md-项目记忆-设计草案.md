## 一、这个功能解决什么

会话内记忆（历史回放）已经在做：模型记得**这次会话里**你写过什么。
但它**跨不了会话**——你关掉终端明天再来，模型不知道「主角叫沈砚」「这座城叫临渊」。

`WWRITING.md` 补的就是这个：**写在创作目录里、用户看得见也改得动、每轮进模型上下文**的项目记忆。

## 三、待议细节

### D1. 骨架的六个小节 — 逐字定成什么？

上游 `renderInitialProjectMemory`（`D:/WWriting/src/core/project-memory.mjs:28-55`）产出：

```md
---
schema_version: 1
---

# WWriting 项目记忆

## 项目定位
- 项目：<title>
- 题材：<positioning>

## 当前有效要求
- <confirmed requirement…>

## 权威文件
- <label>：<path>

## 当前进度

## 持久事实

## 待确认
```

**待议**：

- ① 照抄这份骨架，还是按本项目调整？我的建议是**照抄**——`schema_version: 1` 这个前导块
  让将来程序能稳定解析，六个小节名是对「记忆里该有什么」的成熟划分（定位/要求/索引/进度/事实/待确认）。
- ② **`schema_version` 与事件日志的 `EVENT_SCHEMA_VERSION` 是两套独立版本号**（ADR-0001 说了加事件类型不必升它）。
  这里该怎么写才不让人混淆？建议：在文件里就叫 `schema_version`（对齐上游，便于将来与桌面版互通）。
- ③ `## 权威文件` 那一节是关键——它让 `WWRITING.md` 充当**索引**，
  指向 `OUTLINE.md` / `SETTING.md`，模型再按需用 `read_file` 去读。
  要不要在这里额外记「该文件的字数」或「最后修改时间」？建议**不要**——那是会过期的数字，
  记忆里写过期的数字比不写更糟。
- ④ 小节是**固定**的，但里面留空是允许的（铁律 7 的「不生成固定蓝图」指的是**不预填内容**）。

### D2. 大小上限取多少、超限怎么截？

现成的参照是 `DEFAULT_HISTORY_BUDGET_CHARS = 24000`（历史回放的预算）。

**待议**：

- ① 上限取值。我的建议：**单独一个常量**（别复用历史的那个），值取 **8000 字符**左右。
  理由：`WWRITING.md` 是**索引**不是正文——8000 字已经能写下很长的要求清单；
  它真要大，正确做法是它指向的外面那些文件变大，而不是它自己变大。
- ② 超限时的行为。三个选项：
  - **(a) 只注入索引段 + 前 N 字符**：保住「## 权威文件」那节（索引价值最高），其余截断。
  - **(b) 从头截 N 字符**：简单，但可能把最有价值的索引段截掉。
  - **(c) 不截断，改成注入「路径 + 各小节标题」，全文留给模型用工具读**：最省 token，但多一次工具往返。
  我的建议是 **(a)**：保住索引（它指向真相），并按 Q13 的例外如实说一句截断了。
- ③ 截断事实的**承载面**（审查修正）：沿用既有三件套 `printStatus(text, { final, tone, detail })`——
  主文案 `已载入项目记忆`（守住 2–6 字），数字进 detail（`过长 · 已省略 N 字符`），`final: true` 落 scrollback。
  与历史截断同构（`renderer.mjs:614`：主文案 `已载入前情`，detail `${kept} 轮 · 省略更早 ${dropped} 轮`）。
  分工见 `renderer.mjs:492-495`：detail 是「：一条事实」，note 是行尾量——数字不挤进主状态位。
  这一行就是 Q13 例外（「截断时如实说一句」）的落点。

### D3. 注入失败（文件读不出来 / 权限错 / 编码坏）怎么办？

**待议**：三条路。

- **(a) 降级为「无项目记忆」+ 一条中文事实**，这一轮照常跑。这与历史回放的降级策略**同构**
  （`loadHistory` 失败 → `notice`，不拦发送），是我推荐的做法。
- **(b) 整轮失败**：明显不该——失忆好过开不了工（README 已写这句）。
- **(c) 静默忽略**：违反铁律 3（错误必须给一条用户可理解的事实）。

➡️ 建议 **(a)**，文案与历史回放的降级事实风格一致。

### D4. `WWRITING.md` 不存在时的行为 — 已由审查修正

- ① 读不到文件时，**不是错误**——正常继续，只是没有项目记忆（铁律 7 原文：「缺少 `WWRITING.md`、
  总纲或章节不影响聊天、读取与普通文件编辑」）。
- ② **「缺失」是内容状态，参与每轮判定**。原草案写「只在首轮注入一条提示，之后不再重复」——
  审查否决了它，两条理由：**「首轮」是按轮次计数的事件式判据**，与 ADR-0006 的原则
  （判据是**内容**而不是事件）相反；且撞上统一规格书:376「**用户删除它表示要求重新建立记忆**」——
  会话中途删掉文件后，首轮式提示再也不会出现，Q11 的自主重建静默失效，必须重启会话才恢复。
  修正后的判定与 Q2 的哈希短路同构，只有两种字节形态：
  - **存在** → 注入文件内容（哈希未变则整段复用，缓存命中）。
  - **缺失** → 注入一条**字节恒定**的短提示（如「本项目尚无 WWRITING.md。用户删除它表示要求重建记忆。」）——
    字节不变，前缀缓存照样命中；用户中途删除，**下一轮**模型自然看到缺失并按 Q11 提议重建。
  不需要「轮次」概念；`--continue` 恢复会话后语义也自然成立（判据只看文件此刻在不在）。
- ③ 提示与 D3 的「读取失败」必须**区分**：不存在是常态（上面的固定提示），读失败是异常（D3 的降级事实）。

### D5. `/init` 的更新契约 — 已由审查收敛，除非你反对

上游的合并逻辑是**极保守**的（`project-memory.mjs:60-79` 契约原文）：文件缺失或空白时按
`renderInitialProjectMemory()` 重建稳定模板；文件已存在时**只在「权威文件」稳定小节补充缺失且不冲突的索引**
——不重排用户自由文本、不替换用户已写风格。无缺失索引时返回原内容、不写盘（幂等，不触碰 mtime）。

**审查修正（2026-09-28）**：原草案的选项 (b)「写入前过一道 `mergeProjectMemory` 兜底」**被否决**——
上游那个函数**不是校验器，它自己就写盘**（内容变化时直接 `writeFileAtomic` 到创作目录）。
采纳它等于把「程序写创作目录」这条路搬进来：绕过 `permissions.mjs:22` 的 `WRITE_TOOLS` 确认、
违反 ADR-0007（「应用代码**不得**自动生成或修改它」）、`smoke-windows.ps1:281` 那条
「没有私自生成 WWRITING.md」断言也随之失去意义。

修订后的契约是两层防线，都站在 ADR-0007 这一侧：

- **(a) prompt 职责**（第一道）：system prompt 写明「已有内容谨慎合并、不得无理由整体覆盖、
  必须报告检查依据与实际变更」（统一规格书:375 原文）。上游同款。
- **(b) 确认卡 diff**（真正的防线）：模型调用 `write_file` / `edit_file` 改 `WWRITING.md` 时，
  确认卡**必须显示改了什么**——旧→新的 diff 摘要（Q12 已定「确认卡显示变更」，这是它的具体化）。
  程序在这一步是**只读**的：算 diff、放进确认卡，不写盘、不否决。
  模型真要覆盖用户手写内容时，用户在确认卡上看得见、拒得掉。

**明确不做**：

- **程序自动拒绝某次写入**——「删除了用户段落」无法可靠判定（模型精简冗余是合法的），
  自动否决还会制造「模型写的内容被程序拒绝」这种新交互。
- **程序写盘**——违反 ADR-0007。若将来真要做，前置条件是**先改 ADR-0007** 并论证权限不被弱化，
  那不是本设计的选项。
- **写入后回读校验**——`write_file` 的工具结果本来就带回给模型（活动行含结果摘要），回读是重复机制。

### D6. 屏幕上要不要显示「记忆就绪」状态

现在 `cli.mjs:245` 的启动头部面板已经有一行：`记忆  WWRITING.md 已就绪 / 尚未建立`。
**待议**：这行够不够？我建议**够**——它只在启动时出现一次，符合铁律 3。
不建议在每轮状态里再出现。

### D7. 与首次引导（onboarding）的关系

**待议**：`/init` 与首次配置（选厂商/Key/模型）是**无关的两件事**——
前者建立项目记忆，后者配置模型访问。建议**完全不联动**：
首次引导不问「要不要初始化项目记忆」，因为那需要先有创作目录内容可读。
用户第一次开新目录时，模型看到「尚无 WWRITING.md」会自然提议（Q11）。

## 四、不做什么（明确划界）

- **不做向量检索 / 相关章节召回**：`WWRITING.md` 是索引，不是检索引擎。
- **不做自动摘要**：记忆由模型按确认写入，不是从历史里自动归纳的。
- **不做 `WWRITING.md` 与桌面版 `project.yaml` 的互通**（README 已声明不做互通）。
- **不做多文件记忆**：只有 `WWRITING.md` 一个入口（铁律 7 的原文：「记忆入口」单数）。
- **不做锁**（Q12）。

## 六、事实：DeepSeek 的思考强度怎么表达

> 出处：官方 API 文档 `https://api-docs.deepseek.com/api/create-chat-completion`（2026-09-28 抓取）。
> 档位集合与 `max_tokens` 联动是**服务端行为**，本地无法终验——**实现首日对官方端点实测一次**再定稿。

两套并存的开关，**本项目两套都下发（双发，显式钉死）**：

| 参数 | 取值 | 本项目用法 |
|---|---|---|
| `reasoning_effort` | `none` / `low` / `high` / `max`，默认 `high` | 档位的**唯一用户可见面**（见 D8） |
| `thinking.type` | `enabled` / `disabled`，默认 `enabled` | **防默认漂移的钉子**，不暴露给用户 |

**为什么双发**——上游 `openai-compatible.mjs:123-127` 注释原文：

> 声明 reasoningEffortLevels 的模型一律携带 thinking:{type:"enabled"} 与 reasoning_effort——
> **绝不赌服务端默认（2026-08 实测默认值按时间窗漂移，思考内容时有时无）**。

映射：`low` / `high` / `max` → `thinking:{type:"enabled"}` + `reasoning_effort:<档>`；
`none` → `thinking:{type:"disabled"}` + `reasoning_effort:"none"`。
双发组合的兼容性列入实现首日的实测清单。

原文（官方文档）：*`none` disables thinking mode; `low` / `high` / `max` enable thinking mode.
The default effort is `high`. For compatibility with existing software, `minimal` is accepted and
mapped to `low`, and `medium` / `xhigh` are accepted and mapped to `high`.*

**四条容易踩的连带事实**：

1. **`max_tokens` 默认值跟着它变**（官方文档）：非思考模式 8K / 思考模式 64K / **`max` 时 128K**。
   这是真实的能力差异，不是装饰。
2. **思考模式下 `tool_choice` 的 `required` 与具名选择不被支持**，会返回 400。
   **当前 payload 根本没有 `tool_choice` 字段**（`deepseek-client.mjs:217-224`——省略该字段即服务端默认），
   **当前不冲突**；将来若想强制调某个工具，必须先关思考。
3. **上游规格的「低/中/高」与 API 不是一套**。上游是 UI 抽象（三档），API 是四档。
   照抄「低/中/高」会**丢掉 `max`**（128K 输出那一档）。见 D8 的偏离声明。
4. **`reasoning_content` 只在思考模式下出现**，而你的客户端是**明确丢弃**它的
   （`deepseek-client.mjs:4` 的注释：「reasoning_content 等私有思考字段只丢弃」）。
   这与「思考强度可调」在观感上是矛盾的——见 D10。

## 八、`/effort` 的待议细节

### D8. 档位映射 — 这是对文案规格的显式偏离，不是开放偏好

**审查修正（2026-09-28）**：AGENTS.md 把上游定为「能力与文案的**规格权威**」，统一规格书:156 原文：
「思考强度仅当模型已验证支持时显示 低/中/高，否则只显示 `自动` 且禁用，不伪装生效」。
四档直通是**刻意偏离**这条文案——偏离不一定是错的（CLI 直连 DeepSeek、`max` 档是白丢的能力），
但性质是**规格决策**：采纳 (a) 就必须落 ADR 声明偏离与理由，不能当成顺手的产品选择。

- **(a) 直接暴露 API 的四档**（偏离规格）：`/effort none|low|high|max`，与文档一致，用户查文档时能对上。
  **偏离理由**：CLI 直接对 DeepSeek，没有上游多厂商 UI 的抽象层；`max` 档是真实能力（输出上限 128K），
  三档抽象白丢它。**采纳时落 ADR-0009 声明偏离**。
- **(b) 上游的三档（低/中/高）**（不偏离规格）：与桌面版观感一致，但 `中` 映射到 `high`、**没有 `max`**。
- **(c) 四档 + 中文别名**：`/effort 关|低|高|最强`，同时对英文档位。

➡️ 建议 **(a) 四档直通 + ADR-0009 声明偏离**。中文别名（c）看着亲切，
但会给「哪个词对应哪个档」留出歧义空间——你要的是精确。

### D9. 能力判定 — 问题重构成「能力来源」（审查修正）

上游规格要求「思考强度**仅当模型已验证支持时**显示，否则只显示 `自动` 且禁用，不伪装生效」。
**审查否决了原草案的 DeepSeek 模型名白名单**：`base_url` 是可配置的（`config.mjs:11` 白名单字段、
`config.mjs:149` 环境变量 `DEEPSEEK_BASE_URL` 优先、`deepseek-client.mjs:121` 模型列表取自
`${baseUrl}/models`）——端点可以是**任意 OpenAI 兼容网关**，写死 DeepSeek 模型名的白名单
会把网关下本支持思考的模型**静默判成不支持**。
本项目研究笔记里有真实反例：GLM-5.3 只接受 `max/high/low`，其余报错（`docs/research/04:133`）。
上游自己的路线是**声明式能力字段**（`caps.reasoningEffortLevels`，`openai-compatible.mjs:127`）——
原草案没把它列为候选，漏了。

修正后按「能力来源」三层判定，逐层回退：

- **(i) 已知官方端点内置表**：`normalizeBaseUrl(baseUrl) === DEFAULT_BASE_URL` **且**模型 id 在官方清单
  → 代码内置已知能力，零配置可用。**键是（端点，模型名）二元组，不匹配裸模型名**——网关下的同名模型不可信。
- **(ii) 配置显式声明**（上游路线）：`config.json` 允许按模型声明 `reasoning_effort_levels`
  （如 `["none","low","high","max"]`；GLM 用户可声明 `["max","high","low"]`——
  **档位集合的差异顺带解决**）。网关用户自己声明、自己负责。
- **(iii) 都没有 → 判定不支持**：`/effort` 只显示「自动」且不可选，并**说清禁用理由与出路**
  （「该模型未声明思考能力，可在配置里为它声明 reasoning_effort_levels」）——不伪装、可核查。

被拒的方案与理由不变：乐观下发 + 拦截 400（grokbuild 教训：能在本地拒绝就别让 API 打回来）、
试探一次并缓存（引入隐形的额外请求）。

### D10. 切换的生效时机 + 与「思考过程可见性」的关系

- **生效时机**：建议**下一轮生效**（改一个本地变量，下一次组请求时带上）。
  与 grokbuild 一致，且你的控制器本来就「正在跑的一轮不变、下一条输入生效」——
  **与既有的队列语义天然同构，不需要新机制**。
- **D10 的关键问题**：思考强度可调了之后，**`reasoning_content` 还是丢弃吗？**
  现在它是明确丢弃的（第 4 行注释）。用户把强度调到 `max` 却什么也看不见，会怀疑「到底生效没有」。

  三条路：
  - **(a) 继续丢弃**：最小改动。用户靠**间接证据**判断（响应变慢、`usage.reasoning_tokens` 变多）。
  - **(b) 记进 usage**：把 `completion_tokens_details.reasoning_tokens` 收下来，
    终态行显示`已完成 · 1.2k tokens（思考 0.8k）`——**客观数字，与你的铁律 6 同构**。
    不泄漏思考内容，只给量。
  - **(c) 渲染思考内容**：已作为**第三部分 D14** 独立成线（2026-09-28 用户提出要做）。本条 (b) 与它不冲突：量在终态行 note，内容归 D14。

  ➡️ 建议 **(b)**。理由：它给了用户「强度真的变了」的**可验证证据**（`max` 档思考 token 明显更多），
  而又不碰「不渲染私有推理」那条既有立场。**这也是最省的一条**——`reasoning_tokens` 就在
  `usage.completion_tokens_details` 里，与 Q9 的缓存字段同一处，一次改完。

### D11. UI 放哪 — 你只有斜杠命令

grokbuild 把档位拼在模型名后（`model_id (effort)`），Claude Code 发通知条。

**你手上有的位置**：
- `/effort` 无参时回显当前档位（grokbuild 的做法：`Usage: /effort <levels> (current: high)`）
- `/model` 的输出里加一行「思考强度：high」
- 启动头部面板（`cli.mjs` 的 `panelRows()`）—— 现在有「模型」一行
- `/help` 的命令表

➡️ 建议**全部都要，且都不新开 UI 区域**：
- `/effort` 无参 → 回显当前档位 + 可用档位（**这是主入口**）
- `/model` 的输出里带一行（因为切模型会重置档位，这两件事本来就该一起看）
- 启动面板的「模型」行尾追加 ` · 思考 high`（零新增行）
- `/help` 命令表加一行

**不做**：底部工具栏（你没有）、每轮状态行报档位（铁律 3，噪音）。

### D12. 档位跟着模型走还是跟着会话走？

上游原文：三控件「选择即保存为**项目默认**」。但思考强度**依赖模型能力**——
切到一个不支持思考的模型时，原来的 `max` 怎么办？

➡️ 建议**跟着会话走 + 切模型时校验**：档位存在会话状态里；切换模型时若新模型不支持，
**重置为默认并如实说一句**（不静默保留一个无效档位，也不静默清掉）。持久化暂不做
（与「项目默认」的差距记在未决项里）。

# 第三部分：对话面呈现的两件事（2026-09-28 追加）

> 用户提出的两条呈现需求：① 用户消息要有「对话框样式」、轮与轮分得更开；② 模型思考链可见、渲染做上去。

## 十、事实：上游规格、竞品、官方 API 各自定了什么

**用户消息**（对话样式规格书）：

- :61「用户消息：右侧紧凑浅中性气泡……Agent 消息：左侧无框正文；两者都无头像无署名」。
- :60「回合边界以间距表达，**不引入分隔线**」；:254 用户消息用紧凑中性气泡，Agent 回复无框直出。
- :143 发送后立即显示本地气泡，journal 事件到达后原位收敛。

**思考链**（§4.9，:176-181）——上游**早就定义了完整展示契约**，CLI 现在是零实现：

- 每个模型轮次**恰好一个**思考项，与工具动作按事件 seq 交替排列。
- 运行中：`思考中`（最多两行、按自然片段替换、不推动滚动）。
- 完成：`思考 N 秒`（N = 真实耗时；无时间戳可算时回退 `已完成思考`）。
- 展开三态：`available` → 显示思考全文；`empty` → 「没有可查看的思考内容（本次无输出或该模型不支持）」。
- :117「私有推理正文绝不进入活动行；reasoning 内容的唯一展示入口是 §4.9」。
- :181「reasoning 只经 reasoning_delta / reasoning_completed 进 journal，**绝不写入下一轮模型上下文，也绝不混入 assistant 正文通道**」。

**grokbuild 的做法**（都有代码证据）：

- 用户消息**没有框**：前缀 `❯ `（老终端降级 `> `）+ **整行 ANSI 背景色带**（native 模式 DarkGray）
  实现「长对话里可扫」。注释原文（user.rs:197）：*Elevated band behind user-prompt rows so turns are
  scannable in a long transcript*。多行逐逻辑行、续行缩进对齐；>3 视觉行折叠为 3 行 + ` …`
  （为省略号重排末行宽度，user.rs:379-399）。与 assistant 之间固定 1 空行。
- assistant 纯 markdown，前缀/框/底色/竖条全无（agent.rs:208-218）——两者的区分度全靠用户侧的「前缀+色带」。
- 思考：流式**实时滚尾**（Truncated = `…` + 最后 3 行，thinking.rs:498-504），结束自动折叠一行
  `Thought for Xs`（muted+粗体，thinking.rs:245-254），ctrl+e 会话内 sticky 展开（mod.rs:1410-1414），
  **跨重启不记忆**；默认**不** dim 不斜体（config.rs:590，有测试锁住）。
- 思考文本原样进 `chat_history.jsonl`，回放重演（时长用服务器时间差，防本地计时器冻成 0ms，
  thinking.rs:109-118）。
- 思考**回传**给 API：xAI Responses API 的加密回传，且 sibling 位置必须字节稳定才命中前缀缓存
  （conversation.rs:87-94，有测试锁住）——**这套对 DeepSeek 不适用，见下方官方规则**。

**DeepSeek 官方对回传的规则**（thinking_mode 指南，2026-09-28 抓取）——**按请求是否带 tools 分叉**：

> 若请求携带 tools 参数：历史轮次的 reasoning_content 均应回传给 API，并会被拼接进上下文。
> **若请求未携带 tools**：reasoning_content 无需回传；即使传入 API，也会被忽略，不会拼接进上下文。

**这条与上游规格 :181「绝不写入下一轮模型上下文」存在真实张力**：本项目是 agent，
带工具的轮次 payload 里就有 `tools`（`deepseek-client.mjs:224`）——按官方现行规则「应回传」。
上游写 :181 时的 API 行为（deepseek-reasoner 时代，传入即 400）已经变了：现在是
「不带 tools 忽略、带 tools 推荐回传」。**这是 D14 要你拍板的第二件事**。

## D13. 用户消息的样式 — 「气泡」的终端翻译

**现状**：`printUser`（`renderer.mjs:452-457`）= 一行 `❯ 文本`（accent 前景色），无底色无框，
分隔靠块间距（openBlock）。**首版无多行输入**（`input.mjs:1`「Enter 发送，Shift+Enter 不承诺多行」），
所以用户消息当前必为单行。

**张力**：你要「对话框样式、分明一点」；既有约定「渲染器不画框线」（2026-09-28 删掉了
`printInputRule`——框线贴着输入框会出现两条线）；上游的「气泡」是 HTML 底色圆角，
CLI 得翻译成终端语言。

三条路：

- **(a) 背景色带**（grokbuild 路线，推荐）：用户消息每一行铺一层中性暗底（ANSI 背景 SGR），
  前缀 `❯ ` 保持。「气泡」的终端对应物是**底色**而不是框线——grokbuild 用色带替代框正是同一动机。
  与「不画框线」约定兼容；NO_COLOR 下自动退回现状。实现注意：宽度按显示宽度算
  （`█` 是窄字符的既有教训）；printUser 本来就是整块一次性写，逐行加背景码即可。
- **(b) 真画框**（`┌─┐│└┘`）：「分明」最强，但违反不画框线约定——用户消息框与输入区上下
  两条框线相邻，正是当年删框线的场景；且单行消息套框要占 3 行高度，膨胀 3 倍。
- **(c) 只加轮间空行**：最省，但「空行 + 输入框上边线」正是记忆里「两道分隔」的反例，区分度最低。

➡️ 建议 **(a)**。附带划界：本条只管**历史呈现**；多行输入编辑（Shift+Enter 换行，上游 :139 有）
是另一条线，首版明确不做；长消息折叠（grokbuild 的 >3 行截断）在单行前提下用不上，不做。

## D14. 思考链可见 — 三层拆开，每层独立拍板

**分层**——采集是渲染的前提，组装是独立的开关：

**1. 采集层（必须做，无争议）**：`streamChat` 增加 `onReasoning` 回调读 `delta.reasoning_content`
（现在 `deepseek-client.mjs:299` 有意不读）；思考文本**只进 journal**（新事件，如
`reasoning_delta` / `reasoning_completed`——新增事件类型不必升 EVENT_SCHEMA_VERSION），
**绝不进 text、绝不混入可见正文通道**（上游 :181 的后半句照守）。

**2. 渲染层（本次目标）**：

- 流式中：live 行显示 `思考中`（`printActivity` 的 running 通道现成）。上游「最多两行扫光」的
  **内容片段**上不上屏？终端 live 行只有一行——建议只放状态词，内容不实时上屏
  （铁律 3；且流式思考刷屏会盖住正文的流式感）。这是对上游的**降维**，如实记录。
- 完成后：一行 `思考 N 秒`（muted 色调；N = 该轮真实耗时，clock 可得；无时间戳回退
  `已完成思考`——照抄上游文案表）。grokbuild 的 `Thought for Xs` 与上游在这里语义一致。
- **全文呈现**——终端没有折叠组件，三条路：
  - **(i) 灰显直出**：全文以 muted 落 scrollback。诚实、零交互，但 `max` 档思考可达几万字符，
    直出会把正文冲没。
  - **(ii) 默认一行，命令查看**（推荐）：默认只留 `思考 N 秒`，`/reasoning` 重放**上一轮**
    思考全文（muted 色）。最贴近上游「默认折叠」的语义；代价是一条新命令。
  - **(iii) 键位切换**（grokbuild 的 ctrl+e）：CLI 的键盘被常驻 readline 占着，
    加全局键位复杂，不推荐。
- **回放**：`--continue` 重建时思考项画终态行（时长从事件时间戳算——grokbuild 防 0ms 的教训直接适用）。

**3. 组装层（独立开关，先不回传）**：messages 组装**不带** reasoning_content——对齐上游规格 :181。
**但要在案记录**：DeepSeek 现行规则是「带 tools 应回传」，不回传是**对官方推荐的偏离**；
代价是长工具链里模型每轮重新思考（思考 token 可能花更多），收益是上下文与账单可控、
历史前缀更稳定。**实测一轮工具密集任务后回头定**——D10(b) 收的 `reasoning_tokens` 就是判据。

**与 D10 的关系**：D10(b)（收 `reasoning_tokens` 进 usage、终态行显量）仍然成立且不冲突——
量在终态行 note，内容是本条。原 D10(c)「渲染思考内容」由本条承接。
