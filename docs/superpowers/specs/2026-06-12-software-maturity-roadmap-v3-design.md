3. **用户提出范式级反馈**（2026-06-12）：产品不符合 agent 交互逻辑——"跟 AI 聊不了天，它只是麻木执行写文章"。代码取证证实（用户输入仅两条正则理解；/ask 只读无手脚）。对一个名为 Novel Agent 的产品，这是比单项功能更根本的成熟化议题，且其呈现层会重塑门禁交付形态（故障卡 → 对话提案）。

### S2 拆分说明

- **S2a（保留先行）**：原 S2 spec 的 memory-extractor、continuity 契约、prompt 集成、`audit:rebuild-memory`。它同时是门禁与对话 agent 的共同地基（agent 答"主角设定"靠它）。
- **S2b（并入 S3）**：fact-check / title / word-cap 三门禁的判定机制照原 spec 实施，但**呈现层不再做故障卡 UI**，直接以对话提案消息 + 一键修复交付（S3 spec §7）。原 S2 spec 的设置页"质量门禁"分区、回归语料、`verify:s2-gates-online` 验收全部随 S3 交付。

### 执行顺序与硬约束

S2a → S3（内部分层：loop+读 → 写+确认 → 门禁对话化 → UI 收口）→ S4 → S5。

- 用户已选择 S3 整体一次交付（方案 A）：S2a + S3 合并为一个实施计划、单次验收；内部每层全量测试是过程纪律，不设中间用户验收门。
- S5 发包前 S1–S4 验收必须全部通过（继承 v2 铁律）。
- 真实模型验证常态化（继承 v2）：S2a/S3 验收含真实 API 短跑。

## 设计原则（v2 全部继承，新增一条）

- 花钱的功能必须标价（对话每轮成本可见）。
- 先取证后开发（本次范式转向正是取证驱动）。
- **新增：交互以对话为先**——新功能的用户触点优先设计为 agent 对话行为，按钮/表单是快捷方式而非主路径。

## 明确不做（合并 v2 + S3 spec）

EPUB、插件市场、云同步、账号系统、自动更新器、语音、多项目跨聊、向量检索、对话分支回溯。
