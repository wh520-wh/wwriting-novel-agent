# WWriting 验收缺陷修复设计

日期：2026-06-13
状态：已完成需求确认，待实施计划
依据：`WWriting-真实用户验收报告-2026-06-13.md`

## 1. 背景

2026-06-13 的真实用户验收确认了桌面端启动端口问题已经修复，同时暴露出五项需要继续处理的产品缺陷：

1. 用户点击停止后，在途 fact-check 仍可能持续约 100 秒。
2. “写第 1 章”会越过单个任务范围，自动进入第 2 章。
3. 取消后界面可能显示章节已经定稿，但最终章节文件并不存在。
4. 切换项目后，旧项目的迟到消息可能出现在新项目界面。
5. OpenAI-compatible 模型配置不完整时仍可保存，直到真正调用模型才失败。

这些缺陷并非五个互不相关的界面问题。共同根因是系统缺少以下统一契约：

- 一个队列任务究竟允许执行哪些章节。
- 停止信号应传播到哪些操作。
- 章节、任务和项目分别在什么条件下算完成。
- 哪一层数据是界面展示的最终真相。
- 异步响应属于哪个项目和哪一次界面会话。
- 什么样的模型配置有资格成为活动配置。

本设计采用“任务执行契约”方案，在保持现有架构和旧项目兼容的前提下修复共同根因，不进行事件溯源式整体重构。

## 2. 已确认的产品决策

本设计基于以下已经确认的决策：

1. 点击停止采用立即停止语义。
2. “写第 N 章”采用严格单章语义。
3. 取消后的恢复采用安全检查点断点续写。
4. 不允许跳过未完成章节。
5. 采用结构化任务执行契约，而不是在各阶段增加零散判断。
6. 章节完成提示必须以真实最终产物为依据。
7. 模型配置采用前端提示、后端裁决、运行前防守的三层校验。

## 3. 目标

### 3.1 功能目标

- 精确章节任务只执行指定的一章。
- 批量写作请求拆成有序的单章任务。
- 所有在途模型调用都能被同一个停止信号中止。
- 取消后保留可恢复草稿，不伪造已定稿结果。
- 任务恢复时从最后安全检查点继续。
- 旧项目异步结果不能污染当前项目界面。
- 不完整的在线模型配置不能成为活动配置。
- 用户可以在保存前测试模型连接。

### 3.2 可量化目标

- 点击停止后 500ms 内，界面进入“正在停止”状态。
- 正常网络和供应商遵守请求取消的情况下，5 秒内进入“已停止”状态。
- 停止确认后不得发起新的模型请求。
- 单章任务完成后不得自动生成下一章。
- 未生成最终文件的章节不得显示“已写入本地文件”。
- 项目切换后，旧项目异步响应更新当前界面的次数为 0。
- 不完整 OpenAI-compatible 配置的保存成功次数为 0。

### 3.3 非目标

- 不把整个系统重构为事件溯源架构。
- 不改变现有正文生成、质量门禁和记忆提取的业务算法。
- 不删除用户取消前已经生成的草稿。
- 不承诺中止供应商已经在服务端开始计算的费用，只保证客户端立即停止等待、重试和后续调用。
- 不在本轮加入可配置的“安全点停止”或“双停止按钮”。

## 4. 总体设计

系统增加四条贯穿后端和前端的统一约束：

1. **范围约束**：执行器只能在当前任务契约声明的章节范围内运行。
2. **取消约束**：所有可等待操作共享同一个 `AbortSignal`，取消异常不得被普通降级逻辑吞掉。
3. **产物约束**：章节是否完成由已验证的最终文件决定，而不是由当前阶段名称推测。
4. **归属约束**：异步结果必须同时匹配项目身份和前端加载世代，才能更新界面。

任务生命周期、章节生命周期和项目生命周期分开表达：

| 对象 | 完成含义 |
|---|---|
| 任务 | 当前任务契约声明的工作已完成 |
| 章节 | 最终文件已原子提交，索引和校验和有效 |
| 项目 | 所有目标章节均已完成 |

单章任务完成时，任务可以是 `completed`，章节可以是 `completed`，但项目通常回到 `idle`，不应被标记为 `completed`。

## 5. 任务执行契约

### 5.1 数据结构

任务队列结构升级为 schema v3。每个新任务保留原始自然语言指令，并增加结构化执行契约：

```json
{
  "id": "task-...",
  "instruction": "写第2章",
  "mode": "write",
  "status": "queued",
  "contract": {
    "version": 1,
    "kind": "write_chapter",
    "chapter_start": 2,
    "chapter_end": 2,
    "stop_policy": "immediate",
    "resume_policy": "checkpoint",
    "skip_policy": "reject"
  }
}
```

首版支持的 `kind`：

- `write_chapter`：写当前待写章节。
- `rewrite_chapter`：重写已存在章节，必须由明确的重写入口创建。
- `resume_chapter`：从取消或中断检查点恢复。

普通写作命令不得通过文本相似度隐式变成 `rewrite_chapter`。

### 5.2 指令解析规则

| 用户指令 | 处理结果 |
|---|---|
| `写第 N 章` | 创建一个 `N..N` 单章任务 |
| `续写第 N 章` | 当前章未完成时创建单章恢复任务，否则按明确规则拒绝 |
| `写三章` | 从当前待写章起拆成三个单章任务 |
| `写到第 N 章` | 从当前待写章起拆成多个单章任务 |
| `继续写作` | 绑定当前待写章，只创建一个单章任务 |
| `重写第 N 章` | 创建明确的重写任务，不改变下一待写章 |

对于无法准确解析的普通写作指令：

- 没有运行中或排队中的写作任务时，绑定提交时的当前待写章。
- 已有运行中或排队中的写作任务时，拒绝含糊入队，并提示用户指定章节，避免多个任务竞争同一章。
- 不得把无法解析的指令解释为“持续写到项目结束”。

### 5.3 章节顺序校验

任务启动前执行契约校验：

```text
write_chapter.chapter_start 必须等于当前待写章节
write_chapter.chapter_end 必须等于 chapter_start
chapter_start 不得超过项目 target_chapters
```

校验结果：

- `N > current_chapter_no`：拒绝跳章，返回缺失章节范围。
- `N < current_chapter_no`：拒绝普通写作任务，提示改用明确重写操作。
- `N === current_chapter_no`：允许运行。

校验失败不得修改项目状态、章节索引或任务队列中的其他任务。

### 5.4 执行边界

`runProject` 同时接受项目边界和任务边界：

```js
runProject(projectRoot, {
  taskId,
  contract,
  signal
});
```

执行循环每次进入新阶段前检查：

1. 是否已取消。
2. 当前章节是否仍在任务范围内。
3. 项目是否已达到总目标。

完成 `chapter_end` 后立即返回，不进入下一章：

```json
{
  "outcome": "completed",
  "task_completed": true,
  "project_completed": false,
  "completed_chapters": [2]
}
```

如果该章恰好是项目最后一章，则返回：

```json
{
  "outcome": "completed",
  "task_completed": true,
  "project_completed": true,
  "completed_chapters": [20]
}
```

### 5.5 单章完成后的状态

非末章完成后：

- 章节索引中当前章为 `completed`。
- `current_chapter_no` 推进到下一章。
- `current_stage` 设为 `queued`。
- `project_status` 设为 `idle`。
- 当前任务设为 `completed`。
- 队列可以自动提升下一条明确的单章任务。

没有下一条任务时，执行器保持空闲，不自动按 `target_chapters` 继续运行。

## 6. 立即停止

### 6.1 两阶段状态收敛

停止请求分为两个阶段：

1. API 接收请求后立即写入 `cancelling`。
2. 执行器确认取消并完成必要的状态落盘后写入 `cancelled`。

建议状态转换：

```text
running -> cancelling -> cancelled
running -> completed
running -> blocked
running -> interrupted
```

`cancelling` 是非终态。重复点击停止应幂等返回当前状态，不重复创建事件。

停止 API 的同步响应只表示“停止请求已接收”，不伪装成已经完全停止：

```json
{
  "ok": true,
  "projectRoot": "...",
  "taskId": "task-...",
  "status": "cancelling"
}
```

### 6.2 取消信号传播

运行时只维护一个任务级 `AbortController`。其 `signal` 必须传入：

- 正文生成。
- 修订生成。
- Fact-check。
- 记忆提取。
- 模型重试。
- 重试退避等待。
- 使用模型的技能钩子。
- 旁路中由当前任务触发的受控模型操作。

文件读写通常不可被 `AbortSignal` 真正中断，因此在以下位置调用 `throwIfAborted`：

- 进入文件操作前。
- 文件操作完成后、进入下一阶段前。
- 写入最终产物的提交点之前。

为防止某个调用点漏传信号，`createModelRuntime` 应持有任务级信号，统一的模型调用包装器默认使用该信号。具体阶段函数仍可显式传入信号，以便测试。

### 6.3 取消异常分类

取消必须作为控制流异常向上传播，不得被当成普通模型失败、解析失败或可降级错误。

统一判断函数应覆盖：

- `signal.aborted === true`
- `ProjectCancelledError`
- `AbortError`
- 由本任务控制器产生的取消原因

Fact-check 的错误处理必须遵循：

```js
catch (error) {
  if (isCancellation(error, signal)) {
    throw new ProjectCancelledError(signal.reason ?? "用户停止");
  }
  // 只有非取消错误才允许记录告警并降级跳过。
}
```

模型重试层发现用户取消后：

- 不再重试。
- 立即中断退避计时器。
- 不把取消包装成供应商传输错误。

### 6.4 停止后的禁止行为

进入 `cancelling` 后不得：

- 发起新的模型请求。
- 进入新的流水线阶段。
- 开始下一章。
- 自动提升下一条队列任务。
- 将未提交章节标记为完成。
- 显示成功定稿提示。

## 7. 安全检查点与断点恢复

### 7.1 检查点原则

检查点记录的是“可以安全恢复的位置”，而不是仅记录界面阶段。至少包含：

- `task_id`
- `contract`
- `chapter_no`
- `stage`
- `segment_no`
- 草稿路径及摘要
- 已完成模型调用标识
- 已完成门禁
- 最终产物提交状态
- 创建时间

### 7.2 各阶段恢复规则

| 取消位置 | 恢复行为 |
|---|---|
| planning 前 | 重新进入 planning |
| planning 完成后 | 使用已有计划进入 drafting |
| drafting 中 | 读取已有草稿，从下一个安全分段继续 |
| reviewing 中 | 保留正文，重新执行未完成审查 |
| fact-check 中 | 重新执行 fact-check，不重新生成正文 |
| revising 中 | 从最后已提交修订分段继续 |
| finalizing 提交前 | 重新校验草稿后定稿 |
| 最终文件已原子提交 | 视为章节完成，不重复写入 |
| summarizing 中 | 保留最终章节，只重新执行未完成记忆提取 |

### 7.3 成本和调用去重

每个成功模型调用记录稳定的调用标识，至少由以下信息组成：

- `task_id`
- `chapter_no`
- `stage`
- `segment_no` 或 `attempt`
- 提示模板版本

恢复时只跳过已经成功记录且产物完整的调用。仅记录“请求已发送”不能作为成功依据。

### 7.4 原子提交边界

最终章节采用临时文件加原子重命名提交：

1. 检查取消。
2. 写入临时文件。
3. 校验内容并计算 checksum。
4. 再次检查取消。
5. 原子重命名为最终路径。
6. 更新章节索引中的 `final_path`、`checksum` 和 `completed`。
7. 写入 `chapter_completed` 事件。

步骤 5 到步骤 7 是很短的提交临界区。一旦最终文件已经原子重命名成功，即使此时收到停止，也应完成索引提交，再把停止应用到后续阶段或任务。系统不得留下“最终文件已存在但索引永远未提交”的人为半状态。

## 8. 章节产物真相

### 8.1 后端判定

Dashboard 为每章返回统一的 `artifact` 信息：

```json
{
  "state": "committed",
  "path_exists": true,
  "checksum_valid": true,
  "readable": true
}
```

`state` 支持：

- `none`：没有最终产物。
- `draft_only`：只有草稿。
- `committing`：正在定稿但尚未提交。
- `committed`：最终文件和索引一致。
- `invalid`：索引、文件或 checksum 不一致。

只有同时满足以下条件才是 `committed`：

- 章节索引状态为 `completed`。
- `final_path` 非空。
- 最终文件存在且位于项目允许目录内。
- `checksum` 非空。
- 实际文件 checksum 与索引一致。

为了避免每 1.8 秒轮询时反复计算所有大文件 checksum，服务端可按 `path + size + mtime` 缓存校验结果。文件元数据变化时自动失效。

### 8.2 前端展示

前端不再通过 `current_stage === "finalizing"` 或 `actual_words > 0` 推断章节已经写入。

| 后端真相 | 用户文案 |
|---|---|
| `committed` | 第 N 章已写入本地文件 |
| `committing` | 第 N 章正在定稿 |
| `draft_only` + `cancelling` | 正在停止，草稿将保留 |
| `draft_only` + `cancelled` | 已停止，第 N 章草稿已保留 |
| `invalid` | 第 N 章产物状态异常，可尝试恢复 |

章节文件卡、字数、成功图标和可阅读入口都必须以 `artifact.state` 为依据。

## 9. 项目异步隔离

### 9.1 前端加载世代

前端维护：

```js
let projectGeneration = 0;
```

每次打开、创建、移除或切换项目时递增。每个异步操作启动时捕获：

```js
const requestScope = {
  projectRoot: currentProjectRoot,
  generation: projectGeneration
};
```

响应返回后，只有同时满足以下条件才能更新界面：

```text
requestScope.projectRoot === currentProjectRoot
requestScope.generation === projectGeneration
```

不匹配的迟到响应静默丢弃，不显示 Toast，也不改变线程状态。

### 9.2 显式项目参数

停止、重试、命令提交、聊天和设置更新等项目级写操作应携带 `projectRoot` 或 `expectedProjectRoot`。后端必须返回实际处理的 `projectRoot`。

这可以避免前端发起请求后，服务器全局选中项目发生变化而造成操作归属不明确。

### 9.3 切换时清理

项目切换时清理以下仅存在于内存的状态：

- Toast。
- `liveBlock`。
- `renderedKeys`。
- 本地旁路问答条目。
- 临时线程状态。
- 当前聊天 busy 展示。
- 上一个项目的活动进度和徽标比较基线。

持久化聊天历史、事件和章节信息仍从新项目目录重新加载，不删除任何项目数据。

### 9.4 Toast 归属

项目相关 Toast 记录创建时的 `projectRoot` 和 `generation`。切换项目时移除旧作用域 Toast。全局 Toast，例如应用启动失败，可以不带项目作用域。

## 10. 模型配置完整性

### 10.1 三层校验

1. 前端即时提示：帮助用户在提交前发现缺失字段。
2. 后端保存裁决：不信任前端，阻止无效活动配置落盘。
3. 运行前防守：兼容旧项目和手工修改文件，在产生模型费用前再次检查。

### 10.2 静态校验规则

`mock`：

- 必须有模型名称。
- 不要求 `base_url` 和 API Key。

`openai-compatible`：

- `model_name` 必填。
- `base_url` 必须是合法的 HTTP(S) URL。
- `api_key_env` 必须是合法环境变量名。
- 本机 secrets 中必须已有对应密钥，或本次请求同时提交新密钥。
- 原始 API Key 不写入项目文件、日志、事件或错误消息。

预设一致性：

- MiMo 预设使用 MiMo 官方基础地址和 `XIAOMI_MIMO_API_KEY`。
- DeepSeek 预设使用 DeepSeek 官方基础地址和对应密钥变量。
- 自定义预设允许自定义地址和变量名，但仍必须满足完整性规则。

保存失败时保持旧活动配置不变。

### 10.3 测试连接

新增模型连接测试接口，使用当前表单内容测试，不要求先保存。

连接测试应：

- 发起最小化、低输出上限请求。
- 使用短超时。
- 支持取消。
- 不把测试内容写入项目对话历史。
- 记录不含密钥的审计事件。

错误分类：

| 分类 | 示例 |
|---|---|
| `configuration_missing` | 缺少 base URL、模型名或密钥 |
| `authentication_failed` | 401、403 |
| `model_not_found` | 供应商返回模型不存在 |
| `network_unreachable` | DNS、连接拒绝 |
| `request_timeout` | 测试超时 |
| `response_incompatible` | 成功响应不是支持的 JSON 结构 |
| `provider_error` | 其他供应商错误 |

测试成功仅表示测试当时可用，不替代运行前静态校验。

### 10.4 运行前防守

任务启动前校验有效配置。无效时：

- 不调用供应商。
- 不消耗模型调用预算。
- 任务进入 `blocked`，而不是普通 `interrupted`。
- 返回可操作的配置错误和打开设置入口。

## 11. 兼容迁移

### 11.1 任务队列迁移

schema v2 升级到 v3 时：

- 保留全部原字段。
- 增加 `contract`。
- 增加 `cancelling` 状态支持。
- 保留原始 `instruction` 作为审计来源。

迁移采用惰性加载并原子写回。

### 11.2 旧任务契约生成

- 明确的单章指令按原文字解析。
- 明确范围指令拆成多个新单章任务。
- 旧版运行中任务绑定当前 `current_chapter_no`。
- 中断或取消任务生成 `resume_chapter` 契约。
- 无法可靠解析的排队任务标记为需要用户确认，不猜测跨章范围。

### 11.3 旧取消状态

旧项目可能存在：

- `project_status: cancelled`
- `current_stage: finalizing`
- 章节索引 `status: finalizing`
- 没有最终文件

迁移后不得把它修正为完成。Dashboard 应识别为 `draft_only`，恢复任务从保存的阶段或最近检查点继续。

## 12. 错误处理和可观测性

新增或规范以下事件：

- `task_contract_created`
- `task_contract_rejected`
- `project_cancelling`
- `project_cancelled`
- `chapter_artifact_committed`
- `chapter_artifact_invalid`
- `model_config_rejected`
- `model_connection_tested`

事件数据不得包含 API Key、完整提示词或正文。

建议记录时间指标：

- `stop_requested_at`
- `cancel_observed_at`
- `cancelled_at`
- `stop_latency_ms`

这些指标用于自动化测试和后续真实用户验收，不依赖人工计时。

## 13. 测试设计

### 13.1 单元测试

任务契约：

- 精确单章解析。
- 范围拆分。
- 含糊指令保守绑定或拒绝。
- 跳章拒绝。
- 已完成章节不会隐式重写。
- schema v2 到 v3 迁移。

取消：

- 预取消信号立即失败。
- Fact-check 收到取消后向上传播。
- 重试退避可被取消。
- 取消异常不会被包装成普通供应商错误。
- 进入 `cancelling` 后不再调用模型。

产物真相：

- 文件、索引和 checksum 全部有效才返回 `committed`。
- 缺文件、空路径、checksum 不匹配均返回 `invalid` 或 `draft_only`。

配置：

- OpenAI-compatible 缺 base URL、模型或密钥时拒绝。
- 非 HTTP(S) URL 拒绝。
- 保存失败不覆盖旧配置。
- 错误分类稳定。

### 13.2 集成测试

- “写第 1 章”只生成 `001.md`，模型调用中没有第 2 章。
- “写三章”创建三个任务，并逐章执行。
- 第 1 章未完成时提交“写第 3 章”被拒绝，项目文件不变。
- Fact-check 阶段停止后 5 秒内收敛为 `cancelled`。
- 取消后草稿存在，最终文件、checksum 和完成状态不存在。
- 从 fact-check 检查点恢复时不重新生成正文。
- 最终文件已经提交时，重复恢复不会重复写入。
- 项目 A 请求迟到后不能更新项目 B 的 UI 状态。
- 无效模型配置不会发起网络请求，也不会消耗调用预算。

### 13.3 前端测试

- `cancelling` 显示“正在停止”。
- `cancelled + draft_only` 显示“草稿已保留”。
- `finalizing` 但没有有效产物时不显示“已写入”。
- 旧 generation 的 Dashboard、停止、重试和聊天响应被丢弃。
- 切换项目清除旧作用域 Toast。
- 连接测试按钮展示明确错误类别。

### 13.4 真实用户验收

使用打包后的 Windows 桌面应用复测，至少保留以下截图：

1. 单章任务开始时的任务卡。
2. 第 1 章完成后项目空闲、未进入第 2 章。
3. Fact-check 期间点击停止后的“正在停止”。
4. 取消完成后的“草稿已保留”。
5. 章节目录中不存在未提交的最终文件。
6. 切换项目后没有旧项目消息。
7. 不完整模型配置的即时错误。
8. MiMo 完整配置的连接测试成功。
9. 断点恢复后章节成功定稿。

## 16. 风险与控制

### 16.1 队列迁移风险

风险：旧任务文本无法可靠推断执行范围。
控制：无法解析时阻止运行并要求确认，不猜测连续章节。

### 16.2 取消与原子提交竞争

风险：停止恰好发生在最终文件提交期间。
控制：明确短提交临界区；提交前取消则保留草稿，原子重命名后则完成索引提交。

### 16.3 供应商不及时响应取消

风险：远端服务忽略连接断开。
控制：客户端立即停止等待和后续调用，并如实说明远端费用无法绝对保证。

### 16.4 Dashboard 校验性能

风险：轮询时反复计算章节 checksum。
控制：按文件路径、大小和修改时间缓存验证结果。

### 16.5 前端异步兼容

风险：只修某个请求，其他请求仍可能跨项目污染。
控制：统一封装项目作用域异步操作，不在单个按钮处理器中零散判断。

## 17. 设计结论

本轮修复不应被实现为五个独立补丁。推荐实现一个最小但完整的任务执行契约，并以它为中心统一取消传播、章节产物真相、项目异步归属和模型配置资格。

该方案的核心结果是：

- 用户指令决定任务范围。
- 任务范围限制执行器。
- 取消信号终止所有在途工作。
- 最终文件决定章节完成。
- 项目身份决定异步响应能否展示。
- 完整配置决定模型是否允许启动。

这些约束建立后，验收报告中的五项缺陷可以在同一套可测试规则下得到修复，同时为后续批量写作、重写、恢复和更多供应商接入提供稳定边界。
