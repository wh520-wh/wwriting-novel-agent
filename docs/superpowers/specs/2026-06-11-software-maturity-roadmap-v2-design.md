# WWriting 软件成熟度路线图 v2 设计

本文档取代 `2026-06-01-software-maturity-roadmap-design.md`。旧路线图的 M1 已交付归档，M2/M3 的内容按本文档的新阶段重新划分。

## 背景

v1 路线图（M1 稳定基线 → M2 产品功能成熟 → M3 发布运维成熟）中，M1 已于 2026-06-01 交付：状态写入串行化、任务队列转换契约、长日志尾部读取、诊断 API 全部落地，`verify:local` 全量通过。随后 2026-06-10 的综合修复又完成了故障卡闭环、暂停语义修正、成本双重记账修复、设置写作目标、导航收敛等原属 M2 的内容。

与此同时，软件已经用真实模型（DeepSeek 等）跑过几十章的完整长篇。真实使用暴露的痛点不再是稳定性，而是：

1. **成本与模型行为**：token 消耗高于预期、缓存命中不理想、重试与补写浪费调用。
2. **内容质量门禁**：现有门禁只有字数和悬念结尾，连贯性、重复度、伏笔类问题拦不住。
3. **日常操作体验**：导出归档缺失、运行反馈不完整、部分操作仍需理解内部结构。

下一阶段的目标用户也变了：近期要把安装包分享给其他作者。没有硬期限，按质量推进。

## 总目标

把 WWriting 从"作者自己能用的写作 agent"，推进到"可以放心交给另一位作者使用的软件"：

- 跑一本书的成本可预期、可归因、可控制。
- 章节质量有门禁兜底，不靠人盯。
- 日常操作不需要懂内部结构、不需要打开项目文件夹。
- 安装包发出去，对方能自己安装、上手、跑通、出问题能求助。

## 阶段划分

四个阶段按"用户可感知主题"切分，取代原 M2/M3：

| 阶段 | 主题 | 回答的问题 |
|------|------|-----------|
| S1 跑得省 | 成本与模型行为 | 写一本书花多少钱、钱花在哪、哪些是浪费 |
| S2 写得好 | 质量门禁 v2 | 不靠人盯，软件能拦住哪些坏章节 |
| S3 用得顺 | 日常操作体验 | 不打开文件夹、不记内部细节能不能用 |
| S4 发得出 | 可分享成熟度 | 安装包发给别的作者，对方能不能自己活下去 |

### 新旧映射

- 原 M1：已交付，见 `2026-06-01-m1-delivery-report.md`，关闭。
- 原 M2 中"失败恢复按钮、设置写作目标、项目列表收敛、运行状态真实化"：已由 2026-06-10 综合修复完成，关闭。
- 原 M2 剩余项（导出归档、运行反馈、设置分区展示）：并入 S3。
- 原 M3（升级迁移、打包验证、诊断包、发布 checklist）：全部并入 S4。

### 执行顺序

推荐 S1 → S2 → S3 → S4，但四个阶段彼此独立、各有 spec→plan 循环，顺序可按需要调整。唯一硬约束：**S4 发包给其他作者之前，S1–S3 的验收必须全部通过**——分享出去之后修问题的成本会数倍增加。

### 审计先行

每个阶段的第一个任务都是审计而不是开发：先用真实长跑数据（`cost.json`、`cache_report.json`、`run_log.jsonl`）和代码现状取证，产出缺口清单，经用户确认后才写实施计划。防止做出解决想象中问题的功能。

## S1 跑得省（成本与模型行为）

### 审计任务

用真实长跑项目的成本与日志数据取证：

- 每章平均模型调用次数与 token 分布。
- 实测缓存命中率（provider 原生字段，区分 `cacheMetricsAvailable` 真假）。
- `model_retry` 事件占比，重试成本量化。
- 字数补写轮次分布与补写成本占比。

### 功能范围

- **每章成本归因**：`cost.json` 当前只按 provider/stage 聚合，增加按章聚合；章节卡上能看到"这章花了多少调用/token/钱"。
- **缓存命中实测与修复**：验证 PromptCompiler 稳定前缀在真实 provider（DeepSeek prefix cache）下的实际命中率，定位破坏稳定前缀的动态内容并修复。
- **重试浪费审计**：区分"重试后成功"与"重试后仍失败"的成本，产出量化报告。
- **补写成本治理**：统计补写轮次，优化首轮 prompt，提高一次写够字数的比例。
- **预算粒度升级**：现有熔断只看调用次数；增加金额/token 上限与每章成本预警。

### 验收标准

- 跑一个真实多章项目后，UI 能回答：总花费、每章平均花费、缓存节省了多少、浪费在哪。
- 重试与补写的成本占比有量化报告。
- 设定金额或 token 上限后，超限熔断且可从故障卡恢复。
- 改动前后用同一项目对比缓存命中率，有基准数据。

## S2 写得好（质量门禁 v2）

### 审计任务

从真实长跑章节中收集坏样本（重复、连贯断裂、伏笔丢失），建立回归语料。门禁的好坏用语料的拦截率和误杀率说话，不靠感觉。

### 功能范围

- **重复度门禁**：章内/跨章相似度检测，纯本地计算，零模型成本。
- **连贯性检查**：基于 `memory/continuity.md` 与角色档案的一致性检查；需要模型参与的部分作为可选门禁，明确标注每章增加的调用成本。
- **门禁可解释**：每个门禁失败给出"为什么不过 + 改哪里"，接入现有故障卡体系（该链路已在 2026-06-10 修复中打通）。
- **门禁分级**：硬门禁（不过不许 finalize）与软门禁（警告但放行），用户可配置。
- **实现机制**：新门禁走 skill-runtime 的 `check` hook，复用 suspense-ending 已验证的路径，不另起机制。

### 验收标准

- 回归语料中坏样本有量化拦截率，好样本有误杀率指标。
- 门禁失败在界面上有人话解释和下一步操作。
- 本地门禁零模型调用成本；模型参与的门禁有明确标价且默认可关。

## S3 用得顺（日常操作体验）

### 审计任务

以"新作者第一次用"视角走查全流程（创建→跑→停→恢复→导出），记录每个需要内部知识才能过去的瞬间。

### 功能范围

- **成书导出**：全部章节合并为单个 Markdown/TXT 文件，附书名等元信息。EPUB 本阶段不做。
- **项目归档与日志清理**：界面入口，不需要手动操作文件夹。
- **运行反馈完善**：当前阶段、当前章节、已耗时（引擎已落盘 `stage_entered_at`，前端利用起来）。
- **设置分区展示**：模型、预算、权限、研究、密钥状态分区（原 M2 遗留项）。

### 验收标准

- 用户不打开项目文件夹，能完成创建、运行、停止、恢复、导出全流程。
- 导出产物可直接交付（章节顺序、标题、元信息正确）。

## S4 发得出（可分享成熟度）

### 审计任务

在干净的 Windows 用户环境安装 NSIS 包走完首次使用流程，记录所有翻车点。

### 功能范围

- **首次上手**：空状态引导、API Key 配置引导、第一个项目创建向导。
- **升级与迁移**：版本号策略、project schema 迁移脚本、旧项目兼容验证。
- **诊断包导出**：把 `/api/diagnostics` 数据与相关日志打包成单文件，用户一键导出发给维护者。
- **发布 checklist**：在 `verify:local` 基础上增加安装/卸载/升级三路验证。

### 验收标准

- 一位没参与开发的作者拿到安装包，不需要维护者在旁边，能完成安装→配 Key→建项目→跑完一章。
- 出问题能一键导出诊断包。
- 升级后旧项目仍能打开。

## 验证策略

- **既有防线不动**：`npm test`、`verify:app-shell`、`verify:app-clickability`、`verify:local` 仍是每轮交付的硬门槛。
- **每阶段新增验证物**：
  - S1：真实长跑成本基准报告（同一项目改动前后对比）。
  - S2：门禁回归语料测试（拦截率/误杀率）。
  - S3：导出/归档端到端测试。
  - S4：干净环境安装/升级/卸载验证记录。
- **真实模型验证常态化**：S1/S2 的验收必须包含至少一次真实 API 短跑（基于 `verify:provider-online`），不允许只用 mock 宣布通过。

## 设计原则

从 v1 继承：

- 少用内部词，错误信息告诉用户下一步能做什么。
- 每个状态变化可追踪原因，每个失败可归类。
- 不把无关重构混进成熟度任务。
- 小步推进，无验证不宣布完成。
- 每阶段结束输出"已完成、未完成、风险、下一步"。

v2 新增：

- **花钱的功能必须标价**：任何增加模型调用的门禁或功能，设计时写明每章预计增加多少调用，用户可关。
- **先取证后开发**：每阶段第一个任务是审计真实数据，缺口清单经用户确认后才写实施计划。

## 风险与控制

| 风险 | 控制方式 |
|------|---------|
| S1 优化缓存命中需要动 PromptCompiler 稳定前缀，可能破坏现有缓存行为 | 改动前记录基准命中率，改后对比；回归测试锁住 block 顺序 |
| S2 门禁太严导致章章被拦、写作停摆 | 新门禁默认软门禁观察，有误杀数据后再决定是否升硬 |
| S3/S4 的 UI 工作引发"按钮点不动"回归 | CLAUDE.md 既有防线不变，clickability 探针随新控件同步扩展 |
| 范围再次膨胀 | 每阶段独立 spec；EPUB、插件市场、云同步、自动更新器明确不做 |

## 明确不做

- EPUB 导出（S3 只做 Markdown/TXT 合并导出）。
- 插件市场、云同步、账号系统。
- 自动更新器（S4 只做手动安装包升级 + 数据迁移）。
- 大规模 UI 重设计。
