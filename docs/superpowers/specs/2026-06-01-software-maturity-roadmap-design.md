# WWriting 软件成熟度路线图设计

> 本文档已被 `2026-06-11-software-maturity-roadmap-v2-design.md` 取代。M1 已交付（见 `../reports/2026-06-01-m1-delivery-report.md`），M2/M3 的内容已在 v2 中按新阶段重新划分。

## 背景

WWriting 已经完成了一轮大规模优化：模型调用、流式响应、事件日志、前端拆分、HTTP 错误格式和测试覆盖都有明显改善。

下一步不应该继续做一个更大的“全面优化”，而是要把软件按成熟度分层推进。每一层都要让普通用户和维护者更容易理解、验证和使用。

本设计采用接近 Codex 的策略：

- 先建立稳定基线，再继续加功能。
- 每一步都要有清楚的验证方式。
- 优先解决会影响长期使用的问题。
- 文档和界面都尽量说人话，不靠复杂术语。

## 总目标

把 WWriting 从“功能能跑的本地写作 agent”，推进到“可以长期使用、可以恢复、可以诊断、可以发布的桌面软件”。

用户应该能做到：

- 看得懂项目现在处于什么状态。
- 出错后知道发生了什么，以及下一步该点哪里。
- 停止、重试、恢复时不会担心项目数据乱掉。
- 不需要打开项目文件夹，也能完成主要操作。

开发者应该能做到：

- 用固定命令判断软件是否还能正常工作。
- 出问题时能快速定位到状态、日志、模型调用还是前端交互。
- 每一轮优化都能被审查、回滚和继续迭代。

## 路线图

### M1：稳定基线与交付成熟度

M1 是下一轮优先执行的阶段。

它不追求大量新功能，而是把当前大优化收口成可靠底座。这个阶段完成后，项目应该适合作为后续功能开发的稳定起点。

#### M1 要解决的问题

1. 当前工作区改动很多，需要分清哪些属于本轮优化，哪些是其他变更。
2. 验证命令很多，但还需要明确哪些是快速检查，哪些是完整交付检查。
3. `state.json`、`task_queue.json`、停止、取消、恢复之间的状态竞争需要被验证并消除。
4. 长项目的事件日志会持续增长，需要明确读取和清理策略。
5. 错误已经更多地暴露出来，但还需要让用户和开发者更容易诊断。

#### M1 完成后用户能感受到什么

M1 的很多工作在底层，但用户仍然应该能明显感受到软件更稳：

- 点“停止”后，界面能稳定进入停止或取消状态，不会一会儿显示运行中、一会儿显示已结束。
- 项目恢复或重试时，用户能看懂软件是在继续旧任务，还是创建了新的恢复任务。
- 出错后，用户能看到失败原因和建议操作，不需要打开文件夹翻日志。
- 项目运行很久以后，首页和最近事件仍然能正常打开。

#### M1 功能范围

M1 包含以下工作：

- 整理当前 diff，按后端可靠性、前端拆分、测试、文档、无关变更分组。
- 建立验证矩阵，至少分为快速验证、前端壳验证、点击验证、完整本地验证。
- 加固状态写入，减少停止、取消、恢复、队列推进时出现互相覆盖的风险。
- 明确任务队列的状态转换规则，让 running、cancelled、interrupted、blocked、completed 不互相打架。
- 优化事件日志读取策略，读取最近 N 条事件必须走尾部读取、索引或分页策略，不能为了最近 5 条事件全量读取整个日志。
- 设计最小诊断数据出口，能看到最近事件、模型错误、失败原因和恢复建议。M1 只要求数据出口和已有界面的轻量入口，不做新的大型诊断 UI。
- 输出交付报告，说明已完成内容、剩余风险和延期内容。

#### M1 不包含的工作

M1 不做大规模 UI 重设计。

M1 不新增复杂的云同步、账号系统、插件市场或在线服务。

M1 不把所有历史技术债一次性清完，只处理会影响可靠性、交付和后续开发的部分。

#### M1 验收标准

M1 完成时，应满足：

- `npm test` 稳定通过。
- `npm run verify:app-shell` 稳定通过。
- `npm run verify:app-clickability` 稳定通过。只有在失败被证明是环境问题或已明确接受的非阻塞问题时，才允许记录例外；例外必须写明原因、影响范围和后续处理。
- `npm run verify:local` 稳定通过。只有在失败被证明是环境问题或已明确接受的非阻塞问题时，才允许记录例外；例外必须写明原因、影响范围和后续处理。
- 停止、取消、恢复、重试不会留下互相矛盾的任务状态。
- 缺失状态文件不算错误，坏状态文件会被明确报告。
- 长日志读取最近事件时有受控成本：计划中必须包含一个大日志样本测试，证明读取最近事件不会全量扫描整个日志文件。
- 当前大优化可以被分组审查、提交和回滚。

## M2：核心产品功能成熟

M2 在 M1 稳定后执行。

M2 的目标是让 WWriting 更像普通用户能直接使用的软件。用户不应该需要理解内部文件结构，也不应该需要猜测 agent 正在做什么。

M2 重点方向：

- 项目列表更成熟：最近项目、状态、最后更新时间、主要操作入口。
- 项目详情更清楚：章节进度、任务队列、运行历史、失败记录。
- 失败恢复更容易：针对常见失败给出按钮和说明。
- 设置体验更完整：模型、预算、权限、研究功能、密钥状态分区展示。
- 导出和归档更可靠：用户能把作品导出、备份或清理旧项目。
- 运行反馈更直观：当前阶段、当前章节、模型调用、预计剩余时间更容易看懂。

M2 验收标准：

- 用户不用打开文件夹，也能完成创建、继续、停止、恢复、导出。
- 出错后，用户能在界面里看到原因和下一步操作。
- 任务队列和运行历史能解释项目为什么处于当前状态。

## M3：发布与运维成熟

M3 在 M1、M2 基础稳定后执行。

M3 的目标是让 WWriting 更接近可发布桌面软件。

M3 重点方向：

- 版本升级和数据迁移。
- 打包前验证矩阵。
- 诊断包导出。
- 本地日志清理策略。
- 安装包和升级路径。
- 发布 checklist 和回滚方案。

M3 验收标准：

- 能稳定打包、安装和启动。
- 用户升级后旧项目仍能打开。
- 出问题时可以导出诊断资料。
- 发布前有固定检查流程。

## 推荐执行顺序

推荐按以下顺序推进：

1. 先执行 M1，建立稳定基线。
2. M1 通过后，再为 M2 写单独 spec 和计划。
3. M2 的核心用户流程稳定后，再进入 M3。

这样做的原因很简单：先让地基可靠，再让功能丰富，最后再做发布级能力。

## M1 的第一批任务建议

M1 的实施计划可以从以下任务开始：

1. 工作区变更分组审计。
2. 验证矩阵定义和执行记录。
3. 状态文件写入策略设计。
4. 停止、取消、恢复、重试状态机审查。
5. 事件日志最近读取和长期增长策略。
6. 最小诊断数据出口设计，M1 只做数据和轻量入口，不做大型新界面。
7. M1 交付报告模板。

每个任务都要尽量小，完成后能单独测试和审查。

## 设计原则

### 给普通用户的原则

- 少用内部词，多说“现在发生了什么”。
- 错误信息要告诉用户下一步能做什么。
- 不要求用户理解 JSON、日志文件或内部队列。
- 关键操作要有明确结果，比如“已停止”“正在恢复”“需要处理失败”。

### 给开发者的原则

- 每个状态变化都应该能追踪原因。
- 每个验证命令都要说明覆盖范围。
- 每个失败都要能归类到模型、状态、队列、文件、前端或打包。
- 不把不相关重构混进成熟度任务里。

### 给实施代理的原则

- 像 Codex 一样小步推进：先读上下文，再改最小范围，再验证。
- 不追求一次做完全部成熟度。
- 不在没有验证的情况下宣布完成。
- 每一阶段结束时输出清楚的“已完成、未完成、风险、下一步”。

## 风险与控制

### 风险：范围再次膨胀

控制方式：M1 只做稳定基线，不做大 UI 改版，不新增复杂功能。

### 风险：底层状态改动影响现有流程

控制方式：先写状态转换测试，再改实现；每次只改一个状态路径。

### 风险：验证命令太慢，日常开发不愿运行

控制方式：验证矩阵分层。快速验证用于日常，完整验证用于交付前。

### 风险：文档太工程化，用户看不懂

控制方式：用户界面和交付说明使用简单句，避免只写内部模块名。
