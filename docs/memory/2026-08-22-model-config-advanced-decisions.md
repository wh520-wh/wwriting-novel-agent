## 事实底座（对齐前摸底，全部来自代码，无需用户确认）

- **存储层早就留好了格子**：provider store 每模型已有 `context_window` 与 `max_output_tokens` 字段（`model-provider-store.mjs` `normalizeModel`），校验层也认（`model-config-validation.mjs`、`settings-runtime.mjs`）。当年规格明言高级配置项延期，schema 是预留的。
- **最大输出已经是通路**：`max_output_tokens` 经 `toRequestConfig` -> `active_model` -> adapter 以 `max_tokens` 真实发送（`openai-compatible.mjs:118`）。缺的只是 UI 输入框。
- **上下文字段存而不读**：`runtime.modelConfigOf`（`runtime.mjs:566-584`）的有效窗口只由模型名尾标 `[1m]` 推导（100 万 / 缺省 25.6 万写死），store 的 `context_window` 被 `...active` 带入后即被覆盖，运行时无任何消费点。
- **当前自定义窗口的唯一手段** = 模型名尾巴 `[1m]`；显示串可带尾巴（`model-identity.mjs` 唯一权威注释）。
- **「两个地方」实际是三个显示面 + 一套事件口径**（M5 审计原文）：
  - composer 模型选择按钮（数据路径 dashboard effective，格式「模型名（厂商）」）；
  - 抽屉「模型配置」面板（路径 `buildModelProfile`，格式「厂商 / 模型名」）；
  - 设置页模型行（路径 providers store，裸 `model_name`，可带 `[1m]` 尾巴）；
  - 请求与 `context_usage_updated` 事件用剥尾标基础 ID。
- **设置页已有可折叠先例**：「拉取候选 ▸/▾」（`model-settings-page.js`），高级展开项有现成交互模式可复用。
- 模型行现有能力：模型名行内编辑（失焦/回车保存）、启停、设为默认、删除、测试连接；无任何高级字段入口。

## 决策记录（逐题回填）

### D1（已确认，2026-08-22）：高级项的上下文=真实生效字段；[1m] 尾标机制整条淘汰

- 用户填的 `context_window` 是运行时唯一权威：圆环分母、压缩预检、硬窗口判断全部按它算。
- 用户主动升级的连带决策：**尾标机制不做"手动优先、尾标兜底"的兼容层，直接淘汰**。
- first-principles 判定：与目标模型一致——`model_name` 只是标识符（填什么发什么），窗口大小归数据字段；尾标是"配置走私进标识符"，删除正确。淘汰后三个显示面的名字自然变干净，需求 2 的统一顺势完成一半。
- 迁移语义：并入现有 store 规范化路径一次性完成（名字剥全部尾标；含 `[1m]` 且无显式窗口 → 写 1,000,000）。**线上实际数据零命中**（已验证 `model-profiles.json` 全部 5 个模型名干净、ctx 全 256k），迁移是防御性代码路径，非数据事件。
- 证明死亡清单（prove-dead，实现时逐一核对）：`model-identity.mjs` 尾标解析、`runtime.modelConfigOf` 尾标推导（runtime.mjs:566-584）、`model-connection-test.mjs` 两处 `provider_model_id` 剥离（94/167）、`model-reference.mjs` `stripWindowMarkers`、`context-window.mjs` `window_source` 口径（59）与 `compactionThresholdOf` 两档硬编码（35-37）；相关断言散布 4 个源码 + 9 个测试文件。
- 保留不变：store schema（字段早已预留）、`max_output_tokens` 全链路（adapter 已真实发送）、`modelConfigOf`「运行时副本不写回持久配置」约定、设置页折叠交互先例（拉取候选 ▸/▾）。

### D2（已确认，2026-08-22）：压缩触发点一律 = 窗口八成

- `compactionThresholdOf` 从两档硬编码（256k->204_800 / 1M->967_000）改为 `0.8 × context_window`。
- 用户理由（记录在案）：超长上下文后半段性能明显下降（原话「七八十万之后性能就明显下降」），100 万档宁可早触发（967k -> 800k）。线上无 1M 配置（已验证），行为变化零命中。
- 附带口径：双触发规则保留（达八成，或估算 + 32k 输出余量撞窗口先压缩）；窗口 ≤160k 时余量规则先于八成生效，属预期而非 bug。`window_source` 语义随之改为 `configured` / `default_256k`。

### D3（已确认，2026-08-22）：当前模型信息统一为「厂商 / 模型名」

- 统一格式以抽屉面板为准：`厂商 / 模型名`（如 `DeepSeek 官方 / deepseek-v4-flash`）。
- 统一范围：「当前模型」显示面 = composer 模型按钮 + 抽屉模型配置面板，同格式、同一条取数路径（buildModelProfile / dashboard effective 单源，M5 收口）。设置页模型行是编辑器（裸名字输入框），不套显示格式；尾标淘汰后其名字自然干净。
- 顺带（用户未反对，按推荐收编；缺省值随 D4 更新）：抽屉面板加一行显示「上下文 256k · 最大输出 64k」，高级项填的数字有处可看。

### D4（已确认，2026-08-22）：高级项用预设下拉，不做自由输入

- 上下文窗口预设（k）：**128 / 256 / 400 / 512 / 1000**，缺省 **256**。
- 最大输出预设（k）：**8 / 16 / 32 / 64 / 128**，缺省 **64**。
- 自由数值输入不做 -> 范围/小数校验问题整体消失。存量非预设值（如 API 手写的 192000）在下拉里显示为「当前值」选项，不静默改写。
- **行为变化（用户拍板）**：最大输出缺省从「不发送 max_tokens」改为「发送 64k」。存量 5 个模型（全部未配最大输出）升级后每个请求都带 `max_tokens=64000`。风险一句话：硬上限低于 64k 的提供方可能拒绝请求（当前存量模型无此问题，预设 8–128 可调小）。
- 连接测试不受影响：probe 自带极小 max_tokens（思考型模型探测的既有设计），不走缺省。
